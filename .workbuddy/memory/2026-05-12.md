## 重大定位：sidecar stdin Block-Buffer 问题

通过 stderr 落地拿到决定性证据：6 个 sidecar 进程被反复 spawn，每个 stderr 都**完全空白**（除了我加的 begin/end 标记）。
正常 traceback 一行都没有，说明 sidecar **既没崩溃也没收到任何 RPC 行**。

### 真实根因
`apps/desktop/src-tauri/src/sidecar/client.rs:69` 启动 Python 时**没传 `-u` 参数**：
```rust
let mut cmd = Command::new(python_cmd);
cmd.arg(sidecar_path)  // ← 这里直接是 .py 文件，没 -u
```

Windows 下 Tauri spawn 的 Python 子进程：
- `sys.stdin` 不是 tty，默认 **block-buffered**（buffer 大小 8 KB）
- Rust 写一行 NDJSON（< 200 字节）+ flush，**Python 看不到 `\n`**（因为 buffer 没满）
- `for line in sys.stdin:` 不返回 → sidecar 收不到 RPC → 30s 超时 → Rust 重启 → 再来一遍

为什么 `probe_sidecar.py` 不复现：那个脚本用 `python -u` 启动 sidecar（line 27）。

### 修复（client.rs 增量改动）
1. spawn 时加 `-u`：`cmd.arg("-u").arg(sidecar_path)`
2. 注入 `PYTHONUNBUFFERED=1` 双保险
3. 注入 `PYTHONIOENCODING=utf-8` 防 Win 默认 GBK 解码炸 JSON

新 build：16:29，artifex-nexus-desktop.exe 12MB，setup 3.0MB。

## 第三轮（真正根因）：runtime.is_running() 在新 sidecar 进程里永远 false

新一轮 stderr 日志拿到了关键证据（`-u` + readline 完美生效）：
- 12568 sidecar 跑了 21 个 RPC（含 gateway.start id=13），全部 in/out 成功；最后 stdin EOF 退出。
- 22264 sidecar 跑了 41 个 RPC（全是 status / dcc.port.get 轮询），**全部 in/out 成功**；
  `gateway.start` **没再出现**，但 `gateway_running` 一直返回 false → 前端 waitReady 60 次都没看到 true → 遮罩永不消失。

### 根因
`runtime.py::is_running()`（line 902）：
```python
if _current_openclaw_home:                # ← 新 sidecar 全局 = None
    pid = _read_pid(_current_openclaw_home)
    if pid and _is_pid_alive(pid):
        return True
return False
```

`_current_process` 和 `_current_openclaw_home` 是**模块级全局变量**，sidecar 重启后变 None。
`gateway_state._info` 也是**进程级单例**，sidecar 重启后变 "stopped"。
**两套状态都丢**，永远查不到上一代 sidecar 留下的 gateway。

而 12568 死掉的诱因：前端 React #418 渲染异常 + Mutex 串行 → 某个 RPC 在 Rust 端达到 30s 超时 → manager 杀 sidecar 重启。

### 修复
`is_running()` 在 `_current_openclaw_home is None` 时，用 `OPENCLAW_HOME` 环境变量
或 `~/.artifexnexus/.openclaw` 默认路径 fallback 读 PID 锁文件；命中后还把
`_current_openclaw_home` 自动登记 + 同步 `gateway_state.set_running()`，
让 `openclaw.gateway.status` 也立即变 running。

只改 Python（runtime.py），不需要重 cargo build；sidecar.py 在 release exe 中
通过源码 `packages/adapters/.../sidecar.py` 加载（resolve_sidecar_path() fallback）。
用户重启 exe 即可生效（注意先 kill 残留 sidecar/gateway 进程）。

## 第七轮（18:39-18:50）：GatewayTab 状态仍不一致——PID 锁 vs 实际 PID 不匹配

### 根因深入
PID 锁文件里写的 55808 ≠ 实际 gateway 进程 63560。原因：`openclaw gateway run --force` 是一个 wrapper 命令，`Popen` 返回的 PID 是 wrapper 进程，实际 node.exe gateway server 是 wrapper spawn 的子进程，PID 不同。wrapper 退出后 PID 锁失效，但 gateway 仍在运行。

## 第十轮（19:43-19:48）：React #418 真正根因 — `<div> in <p>` 非法嵌套

### 用户反馈
切对话仍有 `Uncaught Error: Minified React error #418; ... args[]=HTML` 错误。

### React #418 = Hydration Failed
React #418 是 SSR/CSR hydration 不匹配错误，`args[]=HTML` 表明问题出在 **HTML 元素嵌套不合法**。
浏览器在解析非法嵌套（如 `<p>` 内含 `<div>`）时会自动闭合 `<p>` 来"修复"，导致实际 DOM 与 React 期望的虚拟 DOM 不一致 → React 16+ 抛错 unmount 整棵 tree。

### 真正根因
ReactMarkdown 渲染 fenced code block 时输出 `<pre><code class="language-xxx">...</code></pre>`，
而代码块前后通常紧贴段落 → ReactMarkdown 把 `<code>` 节点 wrap 在 `<p>` 内：
```
<p>...<code class="language-json">...</code></p>
```
我们的 `code()` 自定义渲染返回 `<CodeBlock>` 含 `<div>` / `<button>` / `<pre>` —— **块级元素塞 `<p>` 内非法**。
浏览器自动闭合 `<p>` → DOM 不匹配 → React #418 → ChatMessageList 整棵 unmount → "切对话历史消失"。

### 修复（结构性）
1. **hook `pre` 而非 `code`**：fenced code block 在 ReactMarkdown 中输出 `<pre>` 包 `<code>`，hook `pre` 时 CodeBlock 替换的是 `<pre>` 节点，**不会被 wrap 到 `<p>` 内**。
2. **`p` 改为 `<div>`**：彻底消除 `<p>` 内非法嵌套的可能，视觉等价（保留 my-1 间距）。
3. **保留 `code()` 兜底**：处理 ReactMarkdown 边缘情况下直接渲染裸 `<code>` 的场景。
