## 🎯 真凶定位 + Rust SidecarClient 重写（17:58）

### 真凶：BufReader::fill_buf() 在 Windows pipe 上无超时阻塞

完整证据链（exe-stderr-8368.log + sidecar-stderr-45552.log）：
- Sidecar 启动时正常拉起 gateway PID 64184
- 主循环正常处理 RPC：`in/out: dcc.port.get → status → config.dump → dcc.port.get`
- **每条 RPC 都立刻 `out`**（包括 config.dump）
- 但 Rust 端：`→ openclaw.config.dump` 后 30s 才 `✗ FAIL TIMEOUT`
- **响应早就在 sidecar stdout 写完了**，Rust 这边 **30 秒都读不到**

根因：旧 client.rs 用 `BufReader::fill_buf()` 检查是否有数据，但 fill_buf 在 BufReader 内部 buffer 为空时会调底层 `stdout.read()` —— **这是 Windows pipe 上的阻塞 I/O 调用，没有超时**；外层 `Instant::now() >= deadline` 的检查永远不会被执行 → 每条 RPC 都精确卡 30s 才报超时。

### 修复：mpsc channel + 独立 reader 线程

新设计：
- spawn 时启动一个独立 reader 线程，持续 `read_line` sidecar stdout
- 每读一行（trim 后非空）就通过 `mpsc::channel` 推给主线程
- `call()` 主线程：`write stdin + flush + response_rx.recv_timeout(30s)`
- 永不阻塞在底层 read 上 → 30s 超时严格生效

为什么 channel 不会 ID 错乱：SidecarManager 用 Mutex 串行所有 call()，前一个 call 必须完成才能开始下一个，channel 里不会有"上一次响应"残留。

## 启动流程大幅简化（17:50）— 5 处改动

### 设计原则
"流程不要搞得太复杂，越复杂越容易出错"——用户原话。把责任**集中到 sidecar 一处**：sidecar 是 gateway 的父亲负责拉它，前端只读 status。

### 5 处改动（共 -186 行）

#### 1. Rust ExitRequested 强退（lib.rs）
**之前**：handler 调 `manager.call("openclaw.stop")`，若 sidecar 已被 Mutex 卡住，handler 自己也卡 30s，EXE 关不掉，用户只能任务管理器强杀。
**现在**：spawn 后台清理线程 + 主线程立刻 `app_handle.exit(0)` + 1 秒后 `std::process::exit(0)` 双保险。
**效果**：关窗口即退出。

#### 2. Rust manager.call 砍掉 IO 失败重启（manager.rs -37 行）
**之前**：超时/IO 失败 → drop client → spawn 新 sidecar → 重试。出错时旧 RPC 已等了 30s，新 sidecar 抢着接 IPC，多线程级联混乱。
**现在**：错就错，让前端看见，让用户重启 EXE，让 preflight 清理。简单粗暴。

#### 3. Sidecar 主循环之前主动同步拉起 gateway（sidecar.py）
**之前**：sidecar 完全被动，前端调 `openclaw.gateway.start` 才拉 gateway。前端 RPC 链路任何地方异常 → gateway 永远不起。
**现在**：sidecar 启动时（main loop 之前）同步调一次 `_runtime.start_gateway()`，失败也不阻塞。stdin loop 还没开始，没有 RPC 被卡。
**附加**：删掉之前 `_handle_openclaw_status` 里的"按需 ensure" daemon thread 逻辑。

#### 4. 砍掉 `_ensure_control_ui_allowed_origins`（runtime.py）
**之前**：start_gateway 前调 `openclaw config get gateway.controlUi --json`，CLI cold start ~5s + 8s timeout = ~13s 卡顿。
**现在**：注释掉。Control UI 是本地 127.0.0.1 不需要白名单维护；用户真要用可在 SystemPage 手动触发。

#### 5. 前端 AppShell.doCheck 大幅简化（AppShell.tsx -160 行）
**之前**：~200 行复杂逻辑，已运行/未运行两条分支 + verifyAlive + forceRestart 重试 + 30 次轮询。多 IPC 并发抢 Mutex 反成故障源。
**现在**：~50 行——只**轮询 status**，看到 `cli_installed && gateway_running` 就关遮罩。**完全不调** startGateway。删 verifyGatewayActuallyAlive、fetchGatewayAuth 两个 helper。

### 责任划分（新模型）
- **Rust**：preflight 清理孤儿 → spawn sidecar 子进程 → 转发 RPC → ExitRequested 强退
- **Sidecar**：启动时主动拉起 gateway → stdio 处理 RPC（被动）
- **前端**：只读 `status`，看到 ready 关遮罩，没 ready 继续等

## ⚠️ 卡顿根因诊断（17:38）— 待修

### 现象
EXE 启动正常，sidecar 也响应正常（log 显示 in/out 全完成），但 Rust manager.call 全部 30s 超时报"sidecar 响应超时"。每条 RPC（status/dcc.port.get/config.dump）都精确卡 30s。前端永卡"正在检测环境"。

### 排查证据
- sidecar log（pid 15116）：所有 RPC 都 in/out 正常，最后 status 都返回 gateway_running=True
- Rust log（exe-stderr-70940.log）：每条 RPC `→` 后 30s 超时
- 我独立 spawn sidecar 跑同样的 RPC 序列：完全正常 (~2s 返回 config.dump)

### 推断
**Rust SidecarClient 的 stdout BufReader 没读到 sidecar 写入的字节**。
两种可能：
1. **Tauri stdio pipe 的 BufReader 在某次 read_line 后内部状态错乱** — 后续 read_line 永不返回数据，`fill_buf` 持续返回 0 字节但不报 EOF。但实际 sidecar 还在写。
2. **响应被吞掉了**：Rust 写 stdin 后 sidecar 写 stdout，但 Rust 的 BufReader 由于某种原因把数据丢了。

### 二级问题：ExitRequested 不退出
用户 17:33:50 关窗，触发 ExitRequested handler。handler 调 `manager.call("openclaw.stop")` 因为 Mutex 已被 status 卡住的 RPC 持有，自己也卡 30s。**handler 没调 `app_handle.exit(0)`，所以 ExitRequested 没真正退出 EXE**。EXE 70940 至 17:39 仍在跑，前端继续轮询失败。

### 待修
1. ExitRequested handler 改成 spawn 一个线程跑清理 + 主线程立刻 `app_handle.exit(0)` 强制退出
2. SidecarClient::call 加细粒度日志：写入字节数、每次 fill_buf 返回的字节数 + 内容前 100 字节
3. 排查 BufReader 是否被某条响应卡 → 也许换成 mpsc channel + 独立 reader 线程更稳

### 临时绕过
让用户在任务管理器强杀 EXE 进程 → 双击新 EXE。问题会复现，但能强迫 preflight 跑一遍（preflight 这次是工作的：log 显示成功删除 stale lock）。

## EXE 启动/退出统一清理 — preflight.rs（17:10）

### 设计动机（用户原话）
"exe 启动时应该先把测试修复的流程跑一遍，清掉所有占用的进程/端口，如果有老的 exe 在运行也应该先杀掉，同时 exe 关闭时也应该要把这些清掉，然后再启动新的，流程不要搞的太复杂，越复杂越容易出错"

### 实现：`apps/desktop/src-tauri/src/sidecar/preflight.rs`

#### `pre_startup_cleanup()` — 在 `lib.rs::run()` 最早期调用
1. 杀掉所有同名 `artifex-nexus-desktop.exe`（除自己 PID 外）→ **实现单实例**
2. 杀掉所有 `python.exe` 中命令行含 `sidecar.py` 的进程（避免误伤系统其他 Python 脚本如 mcp_bridge）
3. 杀掉占用 19789 (gateway) 和 19791 (browser control) 的 LISTENING 进程
4. 删 `~/.artifexnexus/run/gateway.pid` 和 `sidecar.instance`

#### `post_exit_cleanup()` — 在 `RunEvent::ExitRequested|Exit` 调用
- 先 best-effort 调 `openclaw.stop` 让 sidecar 优雅停（如果还活着且响应）
- 再无脑 kill 所有 sidecar/gateway/锁文件 — 保证下次启动是干净状态

### 关键技术点
- **不引入新 crate**：用标准库 `std::process::Command` + `wmic` / `netstat` / `taskkill`
- **CREATE_NO_WINDOW**：所有子命令带 0x0800_0000 flag，避免黑窗
- **netstat 解析严格化**：检查 `LOCAL` 列以 `:19789` 结尾（避免误杀 connect 到 19789 的客户端进程）
- **跨平台**：Windows 用 wmic/taskkill，非 Windows 用 pgrep/kill
- **全程 best-effort**：所有失败只 eprintln，绝不阻塞 EXE 启动

### lib.rs 改动
1. `pub fn run()` 最开头加一行 `sidecar::preflight::pre_startup_cleanup();`
2. 退出 handler 末尾加 `sidecar::preflight::post_exit_cleanup();`

```ts
  // 同时找到对应"前面那条 user 消息" → 重新入队
  // 有内容/有 toolCalls 的 streaming 占位 → 仅置 isStreaming=false
}
```
重连后，重新入队的消息会自动被 processQueue 驱动重发。

```ts
React.useEffect(() => {
  const sid = state.streamingMessageId;
  if (!sid) return;

    const cur = stateRef.current.messages.find(m => m.id === sid);

      // 60s 没收到任何 chat 事件 → 触发 RESET_STATE 同款恢复
      dispatch({ type: "RESET_STATE" });
```

## v4.1.8 audit log 盲区修复（07:28）

### 用户反馈
触发了一次 Gateway 崩溃。崩溃后用户在弹窗手动点了"重启"。
预期：gateway.log 应有 `[sidecar.audit]` 记录。
实际：**没有任何 audit log**。

### 根因（gateway.log 提供事后证据）
1. **OpenClaw 有 supervisor 包装**（`openclaw.mjs`）：
   - 父进程 = sidecar 启动的 PID（外层 wrapper）
   - 子进程 = 跑业务的 node 进程
   - 子进程崩 → 父进程检测到 child.exit → 自己 `process.exit(1)` → **整个 Gateway 进程死透**
2. **health_monitor 盲区**（runtime.py）：
   - `if proc is None: continue` — 当 sidecar 复用旧 Gateway PID 时，`_current_process = None`
   - → health_monitor 永远不监控复用进程 → 进程死了也没 audit
3. **handle_gateway_start 盲区**（sidecar_gateway.py）：
   - 用户点重启时 Gateway 已死 → `already_running = false`
   - → 不进入 `force_restart && already_running` 分支
   - → 直接 `start_gateway()` 不调用 `stop_gateway()` → 没 audit log
4. **start_gateway 盲区**：未记录每次新启动 / 复用

### 修复（v4.1.8）

#### runtime.py health_monitor
- `proc is None` 时改用 `info.pid + _is_pid_alive(check_pid)` 检测
- 新增 `is_dead`/`exit_code`/`check_pid`/`dead_pid` 中间变量
- audit 区分 `has_proc_obj=true/false`

#### runtime.py start_gateway
- 新进程路径加 `START_GATEWAY:new_process`
- 复用路径加 `START_GATEWAY:reused`

#### sidecar_gateway.py handle_gateway_start
- force_restart 调用必记录 `RESTART_GATEWAY:rpc_called`（含 already_running/state/pid_alive 字段）
- 区分"杀+重启"和"仅重启（Gateway 已死）"

### 改动文件
- `runtime.py`：health_monitor 复用路径检测 + start_gateway audit
- `sidecar_gateway.py`：handle_gateway_start force_restart 必记录

### 关键洞察
**OpenClaw 的 supervisor 机制**意味着：
- 子进程 panic 时父进程**自杀**（exit 1），整个 Gateway 死透

## v4.1.10 端到端耗时埋点（07:45）

### 用户疑问
"信息收发的时间 gateway 检测到的，有时候比我体感的短很多"

### 解答
Gateway 日志的 `[ws] ⇄ res ✓ chat.send 339ms` 只是 **ACK 时间**（确认收到指令）。
真正用户体感时间 = **ACK 时间 + LLM 推理等待 + 流式接收时间**。

```
用户点发送 ──► chat.send ──► Gateway ACK (339ms)  ← 日志显示这段
                                  │
                                  ▼  agent 启动 model_call → LLM 推理 → delta 流
                                  ▼
                              用户看到第一个字 (firstByte) ← 有时几秒到几十秒
                                  ▼
                              final 完成 ← 总时间
```

### 修复（chat-service.ts）
新增 `msgTimingRef: Map<msgId, { sentAt, ackAt, firstDeltaCharsAt, finalAt, runId }>`

每条消息打印 2 条 timing 日志：
1. **首字到达时**：
   `[chat] TIMING msg=... runId=... sent→firstByte=2456ms (ack=339ms, ack→firstByte=2117ms)`
   - 区分"网络往返延迟"和"LLM 等待时间"
2. **完成时**：
   `[chat] TIMING-FINAL msg=... runId=... total=12345ms (ack=339ms + idle=2117ms + streaming=9889ms)`
   - total = 用户体感总时间
   - ack = Gateway 接收 RTT
   - idle = LLM 准备回复时间
   - streaming = 流式接收时间

### 改动文件
- `chat-service.ts`：新增 msgTimingRef + _doSend/_doSendMerged 记 sentAt/ackAt + delta 记 firstDelta + final 打印总耗时
