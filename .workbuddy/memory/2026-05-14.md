## v4.1.2 chat 事件 runId 关联 — 队列空回复彻底修复（00:16）

### 用户反馈
- 队列发送仍触发空回复
- 但信息确实被 Gateway 接收（后面收到正确的回复）
- 后续再发信息逻辑正常，无崩溃

### 根因（gateway.log 持久化首次发挥作用！）
gateway.log 第 53 行揭示真相：
```
[diagnostic] liveness warning: ... eventLoopDelayMaxMs=6249.5
work=[active=agent:...session-...(processing/model_call,q=1) 
      queued=agent:...session-...(processing/model_call,q=1)]
```

同一个 session 内 active + queued = 多个 model_call 同时进行 → Gateway 发出**多个 runId 的 chat 事件交错**：
1. 消息 A 的 delta 流到 → 写入 streaming 占位 #A
2. 消息 B 的 _doSend 完成 → START_STREAMING 创建占位 #B → streamingMessageId=#B
3. **消息 A 的 final 到达** → 旧逻辑无脑 FINISH_STREAMING → **finish 了占位 #B**（错位！）→ B 显示为空回复
4. 消息 B 的 delta 到达 → streamingMessageId 是 null → 防御性 START_STREAMING 创建新占位 #C → 真实回复写入 #C
5. 用户看到 B 空回复 + 一条新消息含真实回复 → "队列空回复但后面收到正确回复"

### 修复（v4.1.2 — 用 runId 关联消息）
- ChatMessage 接口添加 `runId?: string` 字段
- 新增 reducer action：
  - `BIND_RUN_ID { messageId, runId }` — 把 runId 绑到指定消息
  - `APPEND_DELTA { text, targetMessageId? }` — 优先用 targetMessageId，fallback 到 streamingMessageId
  - `FINISH_STREAMING { targetMessageId? }` — 只 finish 指定消息；只在 finish 当前 streaming 时才置 chatState=idle
- 新增 `runIdToMsgIdRef: Map<runId, msgId>` + `runIdToLastTextRef: Map<runId, lastText>`
- 新增 `_resolveTargetMessage(runId, hasContent)` 辅助函数：
  - 有 runId + map 命中 → 返回该消息
  - 有 runId + map 未命中 → 绑定到当前 streaming（如果该 streaming 没绑过）
  - 当前 streaming 已绑别的 runId → 为该 runId 新建占位
- handleGatewayEvent delta/final 全部用 _resolveTargetMessage 找 targetMessageId
- final 处理：清理 runIdToMsgIdRef/runIdToLastTextRef 该 runId 的缓存

## v4.1.3 Gateway 崩溃后空回复修复（00:28）

### 用户反馈
- 队列消息在回复中（一开始没空回复）
- 然后又发了消息 → 崩了 → 变成空回复
- gateway.log 已生效（11966 字节，新启动后正常持续写入）

### 根因
Gateway 进程崩溃时：
1. 第 N 条消息 _doSend 成功 ACK → START_STREAMING 占位 #X
2. **Gateway 在回复任何 chat 事件之前就死了**
3. WS 检测到 disconnected → dispatch RESET_STATE
4. **旧 RESET_STATE 只把 isStreaming 置 false** → 留下空内容空 toolCalls 的 streaming 占位 → UI 永远显示空白消息

### 修复 1: RESET_STATE 智能恢复（chat-service reducer）
```ts
case "RESET_STATE": {
  // 内容空 + 无 toolCalls 的 streaming 占位 → 直接从 messages 移除
  // 同时找到对应"前面那条 user 消息" → 重新入队
  // 有内容/有 toolCalls 的 streaming 占位 → 仅置 isStreaming=false
}
```
重连后，重新入队的消息会自动被 processQueue 驱动重发。

### 修复 2: streaming 60s 超时检测（chat-service useEffect）
```ts
React.useEffect(() => {
  const sid = state.streamingMessageId;
  if (!sid) return;
  const timer = setTimeout(() => {
    const cur = stateRef.current.messages.find(m => m.id === sid);
    if (cur && cur.isStreaming && !cur.content && (!cur.toolCalls || ...)) {
      // 60s 没收到任何 chat 事件 → 触发 RESET_STATE 同款恢复
      dispatch({ type: "RESET_STATE" });
    }
  }, 60_000);
  return () => clearTimeout(timer);
}, [state.streamingMessageId]);
```
即使 WS 没断（gateway 假死），60s 后也能恢复。

1. FINISH_STREAMING 把刚发出消息的占位 finish 掉 → **空回复**
2. 真实的 delta 事件用新 runId 来时 → streaming=null → AUTO-STREAM 创建新占位 → **漂浮新消息**

- 当 `eventState === "final" || "aborted" || "error"` 且 runId 没在 map 中 → **返回 null**（视为 stale 事件，忽略）
- 只有 `delta` 事件 + 首次见 runId + 当前 streaming 没绑过 → 才绑定
- 调用方：`final` 含 message 时仍传 "delta"（视为 delta 语义，需要绑定写内容）；`final` 无 message 时传 "final"

## v4.1.8 audit log 盲区修复（07:28）

### 用户反馈
触发了一次 Gateway 崩溃。崩溃后用户在弹窗手动点了"重启"。
预期：gateway.log 应有 `[sidecar.audit]` 记录。
实际：**没有任何 audit log**。

### 根因（gateway.log 提供事后证据）
1. **OpenClaw 有 supervisor 包装**（`openclaw.mjs`）：
   - 父进程 = sidecar 启动的 PID（外层 wrapper）
   - 子进程 = 跑业务的 node 进程
   - 子进程崩 → 父进程检测到 child.exit → 自己 `process.exit(1)` → **整个 Gateway 进程死透**
2. **health_monitor 盲区**（runtime.py）：
   - `if proc is None: continue` — 当 sidecar 复用旧 Gateway PID 时，`_current_process = None`
   - → health_monitor 永远不监控复用进程 → 进程死了也没 audit
3. **handle_gateway_start 盲区**（sidecar_gateway.py）：
   - 用户点重启时 Gateway 已死 → `already_running = false`
   - → 不进入 `force_restart && already_running` 分支
   - → 直接 `start_gateway()` 不调用 `stop_gateway()` → 没 audit log
4. **start_gateway 盲区**：未记录每次新启动 / 复用

### 修复（v4.1.8）

#### runtime.py health_monitor
- `proc is None` 时改用 `info.pid + _is_pid_alive(check_pid)` 检测
- 新增 `is_dead`/`exit_code`/`check_pid`/`dead_pid` 中间变量
- audit 区分 `has_proc_obj=true/false`

#### runtime.py start_gateway
- 新进程路径加 `START_GATEWAY:new_process`
- 复用路径加 `START_GATEWAY:reused`

#### sidecar_gateway.py handle_gateway_start
- force_restart 调用必记录 `RESTART_GATEWAY:rpc_called`（含 already_running/state/pid_alive 字段）
- 区分"杀+重启"和"仅重启（Gateway 已死）"

### 改动文件

## v4.1.10 端到端耗时埋点（07:45）

### 用户疑问
"信息收发的时间 gateway 检测到的，有时候比我体感的短很多"

### 解答
Gateway 日志的 `[ws] ⇄ res ✓ chat.send 339ms` 只是 **ACK 时间**（确认收到指令）。
真正用户体感时间 = **ACK 时间 + LLM 推理等待 + 流式接收时间**。

```
用户点发送 ──► chat.send ──► Gateway ACK (339ms)  ← 日志显示这段
                                  │
                                  ▼  agent 启动 model_call → LLM 推理 → delta 流
                                  ▼
                              用户看到第一个字 (firstByte) ← 有时几秒到几十秒
                                  ▼
                              final 完成 ← 总时间
```

### 修复（chat-service.ts）
新增 `msgTimingRef: Map<msgId, { sentAt, ackAt, firstDeltaCharsAt, finalAt, runId }>`

每条消息打印 2 条 timing 日志：
1. **首字到达时**：
   `[chat] TIMING msg=... runId=... sent→firstByte=2456ms (ack=339ms, ack→firstByte=2117ms)`
   - 区分"网络往返延迟"和"LLM 等待时间"
2. **完成时**：
   `[chat] TIMING-FINAL msg=... runId=... total=12345ms (ack=339ms + idle=2117ms + streaming=9889ms)`
   - total = 用户体感总时间
   - ack = Gateway 接收 RTT
   - idle = LLM 准备回复时间
   - streaming = 流式接收时间

### 改动文件
- `chat-service.ts`：新增 msgTimingRef + _doSend/_doSendMerged 记 sentAt/ackAt + delta 记 firstDelta + final 打印总耗时

### 构建结果
- TypeScript 零错误
- Tauri build 成功（Rust 58.70s）
- 产物：`artifex-nexus-desktop.exe`

### 验收方式
在 console 看 `[chat] TIMING-FINAL` 即可对比：
- 如果 total >> ack → LLM 慢（OpenClaw / 模型问题，正常）
- 如果 ack >> 100ms → Gateway 内部 RTT 高（EventLoop 退化）
- 如果 streaming 时间长 + 字数少 → 流式速度慢
