## 诊断日志 + 连接中断安全机制 (23:37)

### 问题
DCC 工具运行后 task 永远停在 "running"，polling 一直返回 running 状态。
无法从日志判断执行线程卡在哪里。

### 根因分析
- `get_tool_logger` 设置 `propagate=False`，但 nexus_tool_rpc 使用 plain `logging.getLogger`
  → 日志应能输出到 stderr，但可能被缓冲区延迟
- `_async_call_tool` 在 `_response_queue.get()` 等待时，若 Blender MCP Server 中途断开，
  `_message_reader` 会清理状态但不会唤醒等待者 → 等待者只能等 120s 超时

### 修复

**nexus_tool_rpc.py**:
- 所有关键路径（`_run` 启动、`_execute_tool_sync`、`_execute_dcc_tool` 各步骤）
  添加 `sys.stderr.flush()` 确保日志立即可见
- `_execute_dcc_tool` 添加分步诊断：
  `bridge.is_connected` → `bridge.connect() → result` → `bridge.call_tool() → result`
  每步前后都有 [nt-exec:dcc] 日志 + flush

**mcp_bridge.py**:
- `_message_reader` finally：连接断开时向 `_response_queue` 推入 `None`（sentinel）
- `_async_call_tool` 等待循环：收到 `None` → 立即 raise `ConnectionError`
  → 不再傻等 120s 超时，前端能立即看到连接断开错误
- `_helper` 函数中调用 `_async_call_tool` 时检查 `None` sentinel 避免死等 120s

### 改动文件
- `nexus_tool_rpc.py`：7 处 flush + 分步诊断
- `mcp_bridge.py`：sentinel 推送 + 检查

## ArtClaw 对比 — P1 DCC importlib 回退 + 诊断修复 (23:14)

### 问题
- Example-Blender对象命名规范检查：运行报 "Server shutting down" 
- Example-Blender模型批量加前缀后缀：运行卡住转圈（task 永远 running）

### 根因分析
P1 修复中错误地将 DCC 工具执行改为 `importlib.util.spec_from_file_location` 加载模块。
关键差异：
  - **trigger_dispatcher**：在 Blender **内部**用 `importlib.import_module()`，bpy 全局可用 ✓
  - **MCP Bridge DCC 工具**：代码通过 `exec(code, ns)` 在**预填充命名空间**中运行
    （ns 含 bpy/S/C/D/L/W），但 importlib 让模块在隔离 `mod.__dict__` 中运行
    → 工具代码访问不到 bpy 等上下文变量 → 崩溃 → MCP Server 关闭连接

### 修复
- **回退 importlib**，恢复 raw code 拼接方式
- **新增** `__name__ = '__nexus_dcc_tool__'` 显式设置（在工具代码之前）
  - 既避免 `if __name__ == "__main__"` 守卫被触发
  - 又保留 DCC exec() 预填充命名空间中的所有上下文变量
- **新增** 诊断日志 `[nt-exec:dcc] dcc=... tool=... func=... code_len=...`
- **更新** docstring 说明为什么 DCC 工具不能使用 importlib

### 验证
- Python 编译 ✅
- exec() 模拟测试：DCC 工具正常执行，输出正确 JSON ✅
- `__name__` 守卫测试：`if __name__ == "__main__"` 被正确阻止 ✅
- 工具代码可正常访问 ns 中的 bpy/S/C/D/L/W 上下文变量 ✅

### 最终三项修复汇总

| # | 严重度 | 问题 | 修复 | 文件 |
|---|--------|------|------|------|
| 1 | **P0** | `["python"]` 硬编码 | → `sys.executable`（通用工具 subprocess） | nexus_tool_rpc.py |
| 2 | **P1** | DCC `__name__` 冲突 + importlib 隔离命名空间 | → raw code + `__name__ = '__nexus_dcc_tool__'` | nexus_tool_rpc.py |
| 3 | **P2** | MCP 握手缺 `initialized` 通知 | → initialize 响应后发送 initialized | mcp_bridge.py + nexus_tool_rpc.py |

## UI 约定

### Select/下拉框规范
**必须使用设计令牌，禁止硬编码 `bg-white/[0.0x]`/`backdrop-blur`：**
```
rounded-md border border-input bg-input px-2 text-xs text-foreground 
focus:outline-none focus:ring-1 focus:ring-ring 
[&_option]:bg-card [&_option]:text-foreground
```
- `rounded-md`（6px）= 输入框圆角规范（design-language.md §5）
- `border-input` / `bg-input` = 输入框 L3 色（HSL 0 0% 12.2%）

## Gateway 崩溃/超时问题诊断与修复

### 诊断结论
Gateway 本身**没有崩溃**，真正的问题是 `nexus-tool.fetch_types` 阻塞 sidecar：

**因果链**：
1. `fetch_types` → `bridge.call_tool(timeout=30)` 同步阻塞 sidecar stdin 循环
2. 阻塞期间其他 RPC 全部排队超时 → Rust 端报 "sidecar 响应超时"
3. 每次启动后 30-60s 必定触发（前端轮询 fetch_types）

### 修复（nexus_tool_rpc.py）
- MCP `call_tool` timeout: **30s → 5s**（短超时避免阻塞 sidecar）

## ArtClaw vs Artifex Nexus MCP 通信架构对比

### ArtClaw 架构（参考实现）
- **3 层**：DCC Plugin (MCPServer) ← WS → ToolManager (DCCManager) ← HTTP → Frontend
- **临时 WS 连接**：每次 `execute_on_dcc()` 新建连接 → initialize → tools/call → 关
- **HTTP 健康检查**：DCCManager 轮询 `GET /health`（5s fast / 30s slow 自适应）
- **两级检测**：TCP socket → MCP 握手（先轻后重）
- **进程管理**：简单端口检测 + venv 自动搭建（`tool_manager_launcher.py`）

### Artifex Nexus 当前架构
- **4 层**：Blender MCP ← WS → Sidecar (MCPBridgeClient) ← JSON-RPC stdio → Tauri → Next.js
- **临时 WS 连接**（修复后）：`_fetch_types_via_direct_ws()` 用 `asyncio.run()` 每次新建
- **按需检测**：`check_blender_mcp_connection()` 被动触发
- **复杂 PID 管理**：PID 锁 + sidecar 实例标记 + health monitor + 孤儿清理
- **网关中间层**：MCP 经由 OpenClaw Gateway 转发（多一跳）

### 优劣分析
| 方面 | ArtClaw 更优 | Artifex Nexus 现状 |
|------|-------------|-------------------|
| MCP 连接 | 临时 WS ✓ | 临时 WS（修复后）✓ |
| DCC 检测 | HTTP /health（轻量）| MCP initialize+list（重） |
| 进程管理 | 简单端口检测 | 复杂但健壮 |
| 错误隔离 | 每次独立连接 | 每次独立连接 ✓ |
| 适用场景 | DCC 工具执行 | AI 对话 + DCC 控制 |

**建议**：Artifex 已收敛到与 ArtClaw 相同的"临时 WS per call"模式，核心差异在 DCC 检测层（ArtClaw 有 HTTP health endpoint 更轻量）。当前实现已经足够好。

## Sidecar 重复进程自动检测与清理

### 修改文件
1. **`runtime.py`**：新增 `kill_existing_sidecars()` 函数
   - 启动时用 wmic（Win）/ pgrep（Unix）查找命令行含 `sidecar.py` 的 python 进程
   - 排除自身 PID，对残留进程执行 `_force_kill` + `_wait_pid_dead`
   - 全程 best-effort，失败不阻塞启动
   - 写审计日志 `FORCE_KILL:duplicate_sidecar`

2. **`sidecar.py`**：`main()` 中在 signal handler 注册后、port-drift 自愈前调用
   - 输出 `[sidecar.boot] killed N stale sidecar(s)` 或 `no stale sidecars found`
   - 异常吞掉（`non-fatal`）

### 调用链
```
Rust: preflight::pre_startup_cleanup() → kill_python_sidecars()  ← 第一层
Rust: manager.rs::start() → kill_python_sidecars()                ← 第二层
Python: sidecar.py::main() → runtime.kill_existing_sidecars()     ← 第三层（新增）
```

三层防御确保无论在 dev.bat 重启、Tauri 异常退出、sidecar crash 等场景下都不会积累僵尸进程。

## Nexus Tool 直接运行 — 诊断日志 + 可靠性修复 (22:30)

1. **日志系统初始化**：sidecar 未配置 `logging.basicConfig`，Python 默认仅 WARNING+ 到 stderr。新增 `StreamHandler(sys.stderr)` 设 INFO level，不改变 root logger 级别避免影响其他模块。
