## TASK-0057 Hotfix v3：三态 SendResult + WS 状态可见性 + processQueue 死循环修复（21:54）

### 用户报告问题
1. 重复发送已解决，但右下角弹窗无日志（弹窗概率极高）
2. 发送环境不稳定，高延迟易积压
3. 排队逻辑在消息逻辑混乱后更容易积压
4. artifex 和用户都无法感知 Gateway/WS 状态
5. 右上角显示 WS 已连接，但发消息提示"Gateway 事件循环繁忙"
6. 消息发不到 gateway

### 根因分析
1. **双队列死循环**：`processQueue → _sendQueuedText → ws.sendChat → _enqueueChatSend` 将消息放入 gateway-ws 的 `_pendingSendQueue` → 返回 false → chat-service 保留在 pendingQueue → 下次 retry 被 \_enqueueChatSend duplicate check 拦截 → 再次返回 false → 无限循环
2. **Gateway 回放时 chat-service 无感知**：gateway-ws 回放消息后 chat 事件到达，但 chat-service 无 streamingMessageId → delta 丢失
3. **WS 状态不透明**：Topbar 仅 boolean wsConnected，degraded 时显示绿色"已连接"但实际发送失败

### 修改文件

#### gateway-ws.ts
- 新增 `SendResult` 类型：`{ok:true} | {ok:false, queued:true} | {ok:false, queued:false}`
- `sendChat` 返回 Promise\<SendResult\>（原 boolean）
- `_enqueueChatSend` 返回 SendResult（原 boolean）
- `_doSendChat` 返回 Promise\<SendResult\>

#### chat-service.ts
- `_sendToGateway`：queued=true → ENQUEUE 到 pendingQueue（UI 可见），不 SET_ERROR
- `_sendQueuedText`：queued=true → DEQUEUE（gateway-ws 已接管），不保留在 pendingQueue（**打破死循环**）
- `handleGatewayEvent` delta：无 streamingMessageId → 自动 START_STREAMING（**修复回放响应丢失**）

#### AppShell.tsx
- GatewayContext 新增 `wsDegraded: boolean` + `setWsDegraded`
- Provider 传递 wsDegraded 给 Topbar

#### Topbar.tsx
- 新增 `wsDegraded` prop
- 右上角 WS 指示灯：degraded → 琥珀色脉冲 + "繁忙"（原绿色"已连接"）
- 下拉菜单：degraded → "繁忙"（原"已连接"）

#### ChatView.tsx

## 收发逻辑彻底重构 v4 — 单队列单驱动器（22:59）

### 用户反馈
- 之前 v1-v3 累积修复后逻辑越来越复杂，bug 越来越多
- 实测：Gateway 崩溃 → 重启 → 第二张卡片自己消失但**之前队列消息没发出去** → 再发新消息直接发出（跳过队列）
- 用户原话："整过程非常混乱，你可能需要完整的梳理下逻辑然后重构下"

### 重构原则
1. **唯一队列**：`chat-service.pendingQueue`。`gateway-ws` 不再持有队列。
2. **唯一发送函数**：`_doSend(text)` 只负责发送 → 成功 DEQUEUE_BY_TEXT + START_STREAMING；失败保留消息在队列。
3. **唯一驱动器**：`processQueue()` 检查 ready + idle，从 pendingQueue 取头部发送。
4. **驱动事件**：(a) sendMessage 入队后 (b) FINISH_STREAMING (c) WS ready 变化 (d) EventLoop recovered
5. **防重入**：`sendingRef` 保证同时只有一次 chat.send 在飞，避免双发。

### gateway-ws.ts 简化
- **删除**：`_pendingSendQueue`、`_replaying`、`_replayQueuedSends`、`_scheduleQueueReplay`、`_enqueueChatSend`、`onQueueDrain`、`QueueDrainHandler`、`QueuedChatSend`、`MAX_PENDING_SENDS`
- **新增**：`onReadyChange(handler)` — 当 WS ready/EventLoop 状态变化时通知 chat-service 驱动队列
- **简化 SendResult**：`{ok:true} | {ok:false, reason: "not_ready" | "send_error" | "ack_timeout" | "no_ws"}`（去掉 queued 三态）
- **sendChat 简化**：不可发送时立即返回 `{ok:false, reason:"not_ready"}`，让调用方自己排队
- `_setState("connected")` 延迟 RECONNECT_COOLDOWN_MS+200ms 后触发 `_notifyReadyChange("ws_connected")`
- `_setState("disconnected")` 触发 `_notifyReadyChange("ws_disconnected")`
- health 事件 EventLoop degraded/recovered 触发 `_notifyReadyChange()`

### chat-service.ts 重构
- **删除**：`delegatedToGwRef`、`_sendToGateway`（保留 noop 桩）、`_sendQueuedText`
- **新增**：
  - `sendingRef: boolean` — 防重入
  - `_doSend(text, traceId)` — 唯一发送函数，单条路径
  - `_doSendMerged(text, traceId)` — 合并模式专用路径
  - `processQueue()` — 唯一驱动器，检查 ready+idle 后从队列取头部发送
- **sendMessage 重写**：所有消息统一走 ENQUEUE → processQueue 路径（不再 if-else 分支）
- **驱动事件接入**：
  - `final` 事件 → `queueMicrotask(processQueue)`
  - `health.recovered` → `queueMicrotask(processQueue)`
  - `onReadyChange ready=true` → `queueMicrotask(processQueue)`
- **handleGatewayEvent 删除**：自动 START_STREAMING 兜底逻辑（v4 后所有 chat.send 都先 START_STREAMING）

### 修复的根因
- **Bug A**：双队列 + 双驱动 → 状态不一致 → 消息丢失/重复发
- **Bug B**：onQueueDrain DEQUEUE 循环误删（dispatch 异步 stateRef 不更新）
- **Bug C**：`delegatedToGwRef` Set 与 pendingQueue 不同步 → 死锁

### 关键约束
- pendingQueue 是消息排队的**唯一**真实状态
- 消息只有在发送成功（chat.send ACK 收到）才从 pendingQueue 移除
- sendingRef 同步保证：同时只能有一次 chat.send 在飞
- 所有触发 processQueue 的回调都用 `queueMicrotask` 异步，避免读 stale state
- ws 不 ready / chatState 不 idle → processQueue 是 noop（等下次驱动事件）

### 改动文件
- `gateway-ws.ts`：删除 ~120 行队列相关代码 + 新增 onReadyChange API
- `chat-service.ts`：重写 sendMessage / processQueue / 新增 _doSend / _doSendMerged / sendingRef

### 构建结果
- `npx tsc --noEmit` 零错误
- Tauri build 成功（Next.js + Rust 56.40s）
- 产物：`artifex-nexus-desktop.exe` + `Artifex Nexus_0.1.0_x64-setup.exe`

## v4.1.1 空回复 bug 修复（23:55）

### 用户反馈
- 队列产生了空回复，但信息确实被 gateway 接收（后面才收到回复）
- 再发信息又空回复，且 gateway 崩了
- 最近崩溃概率高

### 根因
- chat-service 的 `case "final"` 处理**完全忽略 event.message** —— 只 dispatch FINISH_STREAMING
- 但 OpenClaw Gateway（`node_modules/openclaw/dist/server-chat-DLVI2zfh.js`）的 final 事件**会带完整 message**
- 协议：delta = 累积式增量；final 也可能含完整最终文本（极快回复 / 协议变种会跳过 delta 直接发 final）
- 当 Gateway 跳过 delta 直接发 final → 前端只看到 FINISH_STREAMING，streaming 占位永远空 → 用户看到空回复
- 第二条消息同样路径，再次空回复

### 修复（chat-service.ts case "final"）
```ts
if (event.message) {
  const lastText = lastTextRef.current;
  const incremental = event.message.startsWith(lastText) ? event.message.slice(lastText.length) : event.message;
  if (incremental) {
    if (!stateRef.current.streamingMessageId) {
      // 防御性创建占位（final 时还没 START_STREAMING 的极端情况）
      const autoMsgId = genMsgId();
      dispatch({ type: "START_STREAMING", messageId: autoMsgId });
    }
    dispatch({ type: "APPEND_DELTA", text: incremental });
    lastTextRef.current = event.message; // 同步累积引用，避免下次 delta 误判
  }
}
dispatch({ type: "FINISH_STREAMING" });
lastTextRef.current = ""; // 为下一条消息重置
```

- gateway.log 持久化 v4.1 已实现，但本次崩溃发生在更早版本，没有日志
