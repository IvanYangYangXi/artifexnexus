## 删除 systemPromptOverride + 多 Agent Skill 共享（22:39-22:46）

### 问题
- OpenClaw agent 无法使用已安装的 Skill（nexus-skill-manage 等）
- 根因：`openclaw.json` 中两个 agent 都配置了 `systemPromptOverride`，导致 OpenClaw 的 `buildEmbeddedSystemPrompt()` 被跳过，Skill 注入段（`<available_skills>` 块）丢失
- `twelve` agent 有独立 workspace `workspace-twelve/`，无 skills 目录

### 已完成修改
1. **删除 systemPromptOverride**（`openclaw.json`）：移除 `artifex-nexus` 和 `twelve` 两个 agent 的 `systemPromptOverride` 字段
2. **AGENTS.md 迁移**：
   - `workspace/AGENTS.md`：追加 Artifex Nexus 专属指令（DCC 桥接、调用规范、安全边界）
   - `workspace-twelve/AGENTS.md`：写入"十二"核心行为准则
3. **多 workspace Skill 联结**（`bootstrap.py`）：
   - 新增 `_ensure_skills_junctions()` 函数 + `_is_junction()` 辅助函数
   - 在 `bootstrap()` 中 `_try_install_official_skills()` 之后调用
   - 用 Windows `mklink /J`（PowerShell `New-Item -ItemType Junction`）创建联结
   - 手动创建了 `workspace-twelve/skills → workspace/skills` 联结
4. **源码验证**：确认 OpenClaw v2026.5.4 的 symlink 处理逻辑（`tryRealpath()` / `fs.realpathSync()`）与 Junction 兼容

### 关键设计决策
- **不配置 systemPromptOverride**：默认不配置，让 OpenClaw 自动注入 skills
- **Junction 方案**：比 copy/symlink 更可靠，Windows 原生支持，双向同步
- **幂等安全**：已存在实体目录跳过不覆盖，已是联结跳过不重建
- **bootstrap 自动创建**：新 workspace 首次启动自动建立联结

### Skill 安装/卸载全链路 QA（23:20-23:30）
全量审查了所有 skill 操作路径，确认 junction 方案下全部正确：

**安装路径**（始终指向 `workspace/skills/`）：
- UI 安装按钮 → `skillInstall()` → Tauri invoke → sidecar RPC `skill.install` → `SkillInstaller._target_skill_dir()` → `_root / skill_name` = `workspace/skills/<name>/`
- Bootstrap 官方 Skill → `_try_install_official_skills()` → `skills_root = openclaw_home/workspace/skills` → 同上
- 两个入口 `_root` 相同（`_DEFAULT_SKILLS_ROOT`），junction 自动镜像到 `workspace-twelve/skills/`

**卸载路径**：`shutil.rmtree(workspace/skills/<name>/)` — 删除真实目录，junction 自动反映

**重装恢复流程**（backup → clean_install → bootstrap → restore）：
1. `_backup_for_reinstall` 备份 `workspace/skills/`（os.walk 不穿透 junction）
2. `_clean_install` 删除整个 `.openclaw/`
3. `bootstrap()` → `_try_install_official_skills` → `_ensure_skills_junctions`
4. `_restore_from_backup` → `_restore_skills` 恢复 skills 到 `workspace/skills/`
5. junction 自动反映恢复后的 skills

**验证通过的关键点**：
- `_WORKSPACE_IDENTITY_FILES` 不含 AGENTS.md → 手动写入的 AGENTS.md 不被覆盖
- `_target_skill_dir()` 始终返回 `_root/skill_name`，不涉及 junction 路径
- `_copytree_ignore_patterns` 用 `os.walk` 默认不跟随 junction → 无循环风险
- 所有 "已安装" 检测均通过 `_resolve_skill_install_dir(workspace/skills/<name>)`→ 一致性保证

## MCP Bridge 重连日志刷屏优化

**问题**：MCP server 未连接时，gateway 每 5 秒刷两条日志（INFO + ERROR），持续刷屏。

**优化**（`packages/adapters/openclaw/gateway-plugin/src/index.ts`）：

| 改动 | 旧值 | 新值 |
|------|------|------|
| `reconnectDelay` | 3000ms | 5000ms |
| `maxReconnectDelay` | 5000ms | 30000ms |
| 日志行为 | 每次都 INFO+ERROR | 前 3 次正常打印，之后静默重试 |
| 成功后 | reconnectAttempts 不清零 | reconnectAttempts 重置为 0 |

**设计**：
- `logSuppressThreshold = 3`：前 3 次保留 INFO/ERROR 便于调试初始连接
- 超过阈值后安静重试，不再刷屏
- 重连成功后重置计数，下次断连从 0 开始

## Chat Tool 调用结果不显示修复（23:32）

### 问题
Chat 界面中，成功执行的 tool 调用只显示参数（args），不显示返回结果（result）；失败的 tool 调用能显示返回结果。

### 根因分析
1. **非 exec 类型 MCP 工具**（如 web_search、数据库查询等）：Gateway 不发送 `command_output` 事件，工具结果仅嵌入在最终 chat message 的 content blocks 中（Anthropic 风格 `tool_result` 块）。
2. **gateway-ws.ts** 的 `_extractText()` 只提取文本 content blocks，`tool_result` 块被丢弃。
3. **chat-service.ts** 完全不处理 `messageBlocks`，导致 tool_result 永不被提取。
4. 失败工具能显示结果是因为 exec 类工具（bash）失败时，Gateway 发送 `command_output` + `exitCode != 0` → `toolOutput` handler 设置 output。

### 修改文件（4 个）

| 文件 | 改动 |
|------|------|
| `types.ts` | `toolCall` 子接口新增 `error?: string` 字段 |
| `gateway-ws.ts` | 导入 `GatewayMessageBlock`；新增 `_extractMessageBlocks()` 提取 content blocks（含 tool_result）；chat 事件传递 `messageBlocks`；toolCall 事件捕获 `error` 字段 |
| `chat-service.ts` | 导入 `GatewayMessageBlock`；新增 `_processMessageBlocks()` 从 content blocks 提取 tool_result → UPDATE_TOOL_CALL.output；delta/final handler 均调用此函数；status 映射修正（failed→error, completed→done）；error 信息写入 output |
| `ChatMessageList.tsx` | ToolCallData 映射：根据 status 分离 result（绿）和 error（红） |

### 数据流
```
Gateway chat event (content blocks: [{text...}, {tool_result: {tool_use_id, content}}])
  → gateway-ws._extractMessageBlocks() → messageBlocks
  → chat-service._processMessageBlocks() → UPDATE_TOOL_CALL { output, status: "done" }
  → ChatMessageList ToolCallGroup → ToolCallItem 显示"结果"段
```
